# PicoSynthSim Architecture

## Goal

PicoSynthSim should help develop and debug an RP2040-based synthesizer/sequencer
from a desktop machine. The real hardware has:

- RP2040 with two ARM Cortex-M0+ cores.
- PIO-driven I2S audio output to a CS4344 DAC.
- 128x128 RGB565 ST7735 display over SPI.
- Four GPIO push buttons.
- Rotary encoder with CLK, DT, and push button GPIO signals.

## Recommended Starting Point

Start with a hardware abstraction boundary, not a full RP2040 instruction set
simulator.

The first useful simulator can model the visible behavior:

- Audio frames generated by the synthesizer.
- Display framebuffer writes.
- Button and encoder input events.
- Simulated time.
- Core-to-core behavior at the level of queues, mailboxes, or shared state.

This gives fast desktop iteration and deterministic tests. It also keeps the
synthesizer logic portable: the real target can bind the same high-level
interfaces to PIO, SPI, GPIO, timers, and multicore primitives, while the host
simulator binds them to desktop audio, a window, keyboard input, and test
fixtures.

## Why Not Full RP2040 Emulation First?

A full low-level simulator would need to approximate or emulate:

- ARM Cortex-M0+ instruction execution.
- RP2040 memory map and peripherals.
- PIO instruction execution and FIFO/DMA timing.
- GPIO edge behavior.
- SPI display traffic.
- Two-core scheduling, interrupts, timers, and races.

That is feasible in principle, but it is a large emulator project before it is a
synthesizer simulator. It is most valuable later for firmware validation,
timing-sensitive bugs, or regression tests against compiled firmware images.

Also, the firmware artifact is normally a UF2 file, not UTF2. UF2 is useful for
flashing and distribution, but not the most convenient boundary for early host
simulation.

## Suggested Layers

1. Portable synth/sequencer core

   Pure C++ or Rust logic with no direct dependency on RP2040 registers. This
   owns oscillators, envelopes, sequencing, UI state, and rendering decisions.

2. Hardware abstraction layer

   Small interfaces for audio output, display writes, buttons, encoder events,
   time, and inter-core communication.

3. RP2040 backend

   Implements the abstraction using PIO I2S, ST7735-over-SPI, GPIO interrupts or
   polling, timers, and multicore support.

4. Desktop simulator backend

   Implements the same abstraction using a Rust host app. The first backend can
   be deterministic and headless. A later backend can provide a window, live
   audio output, and interactive controls.

5. Optional emulator backend

   Only after the abstraction proves too high-level for some bugs, consider an
   instruction/peripheral emulator path for compiled firmware.

## First Milestones

1. Define simulator interfaces for audio, display, input, and time.
2. Build a headless Rust simulation harness with deterministic tests.
3. Add a tiny demo device that emits audio samples and draws to a framebuffer.
4. Add a desktop UI/audio backend.
5. Decide how the C++ firmware core should cross the Rust boundary:

   - Compile portable C++ into a native host library and call it via FFI.
   - Compile portable C++ to WebAssembly and drive it from Rust.
   - Reimplement the portable core in Rust if the firmware is still early.

## Current Recommendation

Keep the firmware/hardware split deliberate from the beginning. Model PIO I2S as
an audio stream at the abstraction boundary for now. Model the ST7735 as a
128x128 RGB565 framebuffer. Model GPIOs as semantic input events unless testing
debounce or encoder edge decoding specifically.

This keeps the early simulator useful and small, while preserving room for
lower-level RP2040, PIO, and GPIO simulation where it pays off.

## Repository Layout

```text
firmware/
  hal/
    lcd_1in44.h              Shared display driver API.
  synth_core/
    synth_c_api.h            C ABI exported by the portable synth core.
    hardware.h               Target-independent input event API.
    synth_app.cpp            Shared application startup and loop.
    synthesizer.cpp/.h       Portable note/message/audio rendering engine.
    voice.cpp/.h             Per-voice oscillator and envelope logic.
    gui.cpp/.h               Imported button/page UI logic.
    midi.h                   MIDI note names and frequencies.
    GUI_Paint.c/.h           Target-independent drawing library.
    Fonts/                   Font tables used by GUI_Paint.
  rp2040_backend/
    main.cpp                 Pico SDK application placeholder.
    lcd_1in44_rp2040.cpp     Real ST7735 backend placeholder.
    hardware_rp2040.cpp      GPIO/rotary event implementation.

simulator/
  desktop/
    build.rs                 Compiles the portable C++ synth core for desktop.
    cpp/sim_main.cpp         Desktop startup shim for firmware-style setup.
    src/lib.rs               Simulated hardware backend.
    src/main.rs              Native window that shows the LCD framebuffer.
```

The current startup/display flow is:

1. A backend allocates the startup-owned `screen` buffer:

   ```c
   const UDOUBLE IMAGESIZE = LCD_1IN44_HEIGHT * LCD_1IN44_WIDTH * 2;
   UWORD *screen = (UWORD *)malloc(IMAGESIZE);
   ```

2. The backend passes `screen` into `synth_app_start(screen)`.
3. Shared C code initializes the Paint library on that buffer.
4. Shared C code clears the display and draws text.
5. Shared C code calls `LCD_1IN44_Display(screen)`.
6. The RP2040 backend will send the buffer to the real ST7735.
7. The desktop simulator backend captures the buffer and displays it in a window.

The current input flow is:

1. Shared C code calls `init_hardware()` from `synth_app_start(screen)`.
2. Each backend provides `init_hardware()` and `get_event(hw_event_t *event)`.
3. Shared C code calls `synth_app_loop(screen)` repeatedly.
4. `synth_app_loop()` polls one event with `get_event()`.
5. The desktop backend maps `1`-`4` to buttons, `Enter` to the rotary switch,
   and the mouse wheel to rotary movement.

The current audio flow is:

1. Shared C++ code calls `Audio::Synthesizer::start()` during app startup.
2. UI events call `Audio::Synthesizer::note_on()` and `note_off()`.
3. The portable synthesizer stores those note messages in an internal queue.
4. The desktop simulator starts a host audio thread.
5. That audio thread repeatedly calls `synth_audio_render_interleaved_i16()`.
6. The render function drains queued note messages and fills stereo `i16`
   samples.
7. On Windows, the simulator sends those samples to the system audio device via
   `waveOut`.

The synth core treats audio as signed 16-bit PCM. That matches the PCM510xA I2S
requirement for binary two's-complement audio data. The RP2040/PIO boundary can
pack those signed samples into `uint32_t` FIFO words with the same 16-bit sample
bit pattern in both channels:

```c
sample_word = (left_bits << 16) | right_bits;
```

This packed word may look "unsigned" in C because it is carried by `uint32_t`,
but the DAC interprets the transmitted sample bits as two's-complement PCM.

This models the RP2040 two-core split at the behavioral level: the UI loop and
audio generation run independently, communicate through a message queue, and the
audio side owns continuous sample rendering.

Run it with:

```sh
cargo run -p pico_synth_desktop_sim
```
